# ADR 0007 — Sync engine (P3)

- Status: **Proposed** — owner review required before merge (touches data integrity; PLAN §10 P3.4)
- Plan: §3.2, §4 · Builds on ADR 0005

## Context
PLAN §4 fixes the model: server is the source of truth, every device keeps a full local copy, writes go to local SQLite
and an outbox, push/pull with a monotonically increasing `server_seq`, last-writer-wins per row by hybrid logical clock.
This ADR records the choices the plan left open.

## Decisions
1. **HLC** (`packages/sync/src/hlc.ts`): `<wall ms, 12 hex>-<counter, 4 hex>-<node id>`. Fixed width, so string
   comparison *is* the clock order and ties between devices break on the node id. A device's clock is strictly
   increasing (also across a wall-clock step back and across restarts: it is seeded with the highest stored `hlc`), and it
   folds in every value it pulls (`receive`) so a later local write always sorts after what the device has seen. Remote
   values more than 24 h ahead of the local wall clock are ignored by the clock (a device with a broken clock cannot drag
   the others forward) and rejected by the server (`hlc_future`).
2. **Conflict policy** (`resolveConflict`): last-writer-wins *per row* by HLC; equal HLC = same write (a retry or the echo
   of our own push). Exception from the plan: on `transactions`, `categorization_method = 'user'` beats any other method
   regardless of the clock. Both sides order rows by the key *(is user-categorized, hlc)*, which is a total order, so
   applying the same rows in any order gives the same winner.
3. **Outbox is filled by triggers**, not by repository code. AFTER INSERT / AFTER UPDATE triggers on all 14 synced tables
   upsert `(table_name, row_id)` into `outbox` (deletes are tombstone updates). This is the single choke point: no current or
   future write path can forget it, and P4+ repositories get it for free. Frozen into migration `0002`; `sync.test.ts`
   fails if `SYNC_TABLES` and the migration drift, so a new synced table must ship its triggers.
   - Deviation from the plan's "row snapshot" column: the outbox stores *which* row changed, and the push reads the row's
     **current** state. Only the latest state of a row matters (LWW), this avoids stale snapshots and keeps the triggers
     free of JSON functions (wa-sqlite on web may not ship them).
   - Entries coalesce per row; an acknowledgement clears an entry only while its `hlc` still matches what was sent, so an
     edit made during a push is never lost.
   - Applying server rows runs with the `outbox_suspended` marker in `sync_meta`, so pulled rows are not echoed back. The
     server sets it permanently (its writes are not a device outbox).
3b. **Wire format**: a row travels as its database record (snake_case, scalar values, booleans 0/1). `validateSyncRow`
   checks it against the table's columns (unknown/missing columns, NOT NULL, integer vs real, booleans) on the server.
   Money rules (signs, splits adding up) are enforced by the authoring client's repository, not re-checked per row.
4. **Server** (`apps/server/src/sync`): `server_seq` comes from a counter row in `sync_meta` incremented inside the push
   transaction (`better-sqlite3` is single-writer, so seqs commit in order and a pull never skips one). The server forces
   `user_id` to the authenticated user; a row owned by someone else is refused (`forbidden`). A push whose row loses to the
   stored one is answered `stale` with the stored row, so the client converges immediately. Retried pushes are idempotent.
5. **Schema versions**: `schemaVersion` = number of bundled migrations. The server refuses an older client (`409
   schema_outdated`, the app asks the user to update) and a newer one (`server_outdated`).
6. **First sign-in** (`SyncStore.enroll`): re-stamps every local row from the placeholder user `local` to the server user
   id (ADR 0005) and, because the outbox triggers are active, queues all of them for the first push.
7. **Engine** (`packages/sync/src/engine.ts`): pure, with injected store, transport and timers. One sync = push until the
   outbox is empty, then pull until `hasMore = false`; syncs never overlap. Triggers: start, foreground, after a local write
   (debounced 2 s), every 5 min, manual.

## Consequences / open points (owner)
- **Default categories are seeded per device** with random ids. Two devices that seed before their first sync create
  duplicate "Supermercado", "Saúde"… rows (same `system_key`, different ids). Merging them rewrites ids on user data, which
  PLAN §0 reserves for the owner. Recommendation: on first enrolment of a device against a non-empty server, map each local
  seed category to the server's category with the same `system_key` (rewrite references, then drop the local copy). Not
  implemented.
- **No sign-in UI yet.** P3 lists no task for the device login (TOTP) screens, so the app has the engine, the HTTP transport
  and the status indicator, but no way to obtain a session. Needs a decision (own task before P3 is usable end to end).
- Attachments sync as rows only; the files themselves (P2.6b) are not part of this protocol.
- `fx_rates` is server-only and not synced.

## Tests (P3.4)
`apps/server/src/sync/convergence.test.ts` (fast-check, 40 runs): 2-3 devices with clocks skewed ±1 h make random edits
(accounts, categories, tags, transactions, transfers, deletes) while offline, with randomly lost push responses; then all
sync. Asserted: every device equals the server row for row, nothing is pending/failed, and the surviving version of every
row is the one the policy prescribes among *all versions ever written* (audited with triggers on each device). Mutation
check: replacing last-writer-wins by "incoming always wins" makes the property fail. HTTP/auth is covered separately by
`sync.test.ts`; the property test calls the sync service directly to stay fast.

Not verified: the migration-0002 triggers on web (wa-sqlite) — the in-app preview is not cross-origin isolated, so the web
database could not be opened there; the triggers use only plain SQL (upsert in a trigger body needs SQLite ≥ 3.24).
