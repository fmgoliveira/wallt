# 0010 — Internationalisation (P7.1)

## Context
PLAN §10 P7.1 requires every user-facing string to be translatable (PT + EN). The app had no i18n layer.

## Decision
- **i18next + react-i18next** (owner approved), device language via `expo-localization`.
- Catalogues are typed TS objects in `apps/app/src/i18n/locales/` (`en.ts` is the source; `pt.ts` must match its keys, so a missing translation fails typecheck). Keys are type-checked at call sites via i18next `CustomTypeOptions`.
- Language preference `system | en | pt`, stored with the same key-value store as security settings (`localStorage` on web, secure store on Android). `system` picks the first supported device locale, English otherwise.
- The language is applied after mount (like the theme) so static HTML and hydration agree.
- Text the user typed or seeded (accounts, categories) is data and is **not** translated.

## Consequences
- Screens are migrated in slices (shell/settings first, then the rest); untranslated screens stay English until migrated.
- New strings go in both catalogues; there is no runtime fallback gap for keys because PT is type-checked against EN.
